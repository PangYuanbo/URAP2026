Architecture Note · URAP 2026

What we add on top of
YOLOMG / TransVisDrone

We keep the existing detector and add one module: a language-free Vision-Action transformer (VATD) that scores how UAV-like a candidate's motion is, then soft-rescores the detector's output. This note covers where it sits, what it reads, and what it outputs.

PART 1Where the module sits

The base detector is left untouched. We run YOLOMG or TransVisDrone at a low threshold so that weak candidates — the few-pixel ones usually discarded — survive. On top of those proposals we add a chain: link weak detections into short tracklets, pass each tracklet through the VATD video/action transformer, and use its output to softly rescore the per-frame detections. The base detector keeps its job; we only add a motion-aware second opinion.

This is not a new detector. It is TransVisDrone / YOLOMG proposals + an action model + soft fusion — action-conditioned track-before-detect rescoring on top of existing proposals.

PART 2Linking boxes into tracklets

A low threshold returns many weak boxes per frame: a few are the drone, most are background clutter (specks, edges, compression artifacts). We link boxes that move coherently across frames into a tracklet, then judge each tracklet by its trajectory instead of any single frame. Plotting the box centres over frames looks like this.

Each tracklet is passed to the model as a trajectory. A smooth path scores high; a jittery cluster or static speck scores low. The output is a soft score, so a weak but coherent drone path is kept, not deleted.

PART 3Difference from TransVisDrone

TransVisDrone uses time as an image feature: it stacks frames so the detector spots the drone better. We use the trajectory instead, asking whether the box moves like a UAV across frames. Smooth UAV-like motion raises the score; erratic motion lowers it.

PART 4What an action chunk is

For each tracklet we convert boxes to actions. A box is [cx, cy, w, h]; the change between frames is one action [dx, dy, dlog w, dlog h] (centre shift + log size-ratio). From the past N boxes the module predicts the next H actions — that sequence is the action chunk. The action is the box's own near-future motion, not a robot command.

PART 5Inside the VATD module

Per tracklet the module reads three inputs: the image crops along the tube, a normalized state token (box, score, visibility), and a motion feature. A temporal transformer fuses them and two heads read out. The main head classifies drone-like motion (binary cross-entropy); its probability is the score we use. The auxiliary head regresses the future action chunk (residual over constant velocity, smooth-L1) as a dynamics prior. No language branch — it is Vision-Action.

PART 6Soft rescore, not hard filter

The action model does not delete candidates. Its confidence adjusts the detector score up or down (soft fusion), so a weak but real tiny drone can still pass. Used as a hard filter it drops too many true tiny tracklets and recall collapses (AFDR ≈ 0.535). As a soft rescorer at center=0.20, β=0.40 on the official AOT evaluator, detection rate rises (AFDR 0.86847 → 0.90859) while false alarms fall (FAR 89.48 → 83.55, FPPI 0.26232 → 0.26193) at the same encounter count (162/175).

Scope: this is a verified gain on the official AOT evaluator, but it is still proposals + action model + soft fusion, not an end-to-end detector, and NPS is not yet a clean win. A gap-insert variant worsened false alarms (FAR 94.88), so the mainline is the action rescorer, not gap insertion.

PART 7Ego-adaptive variant

Heavy host-platform motion contaminates the observed action: the target may be still but the box moves with the camera. The latest module conditions on a camera-motion feature and keeps several look-back horizons (3, 5, 7 frames), each with its own heads. A router reads the ego feature and produces softmax weights to blend them — steady camera leans long, shaky camera leans short. Action supervision is also down-weighted when the camera is unstable.
